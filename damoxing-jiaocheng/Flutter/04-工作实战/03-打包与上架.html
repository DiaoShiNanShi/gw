03-打包与上架

大白话版 · 打包与上架（小白向）
目标：搞懂 iOS/Android 打包流程（含签名）、TestFlight 分发、App Store 上架避坑、Android AAB 与上架、版本管理。

一、先讲"是什么"：打包上架到底在干什么？

一句话版本：把代码"变成"一个能装到手机里的安装包，然后交给应用商店审核上架。

打个比方（餐厅开分店）：

  • 打包 = 把你的菜谱（代码）+ 食材（资源）做成"标准套餐"，包装成一份可以送到任何一家店的"中央厨房成品"（安装包）
  • 签名 = 给这份套餐盖上"防伪章"（数字签名），证明"这是我出的，没被篡改"
  • 上架 = 把成品提交给"市场监管"（App Store / Google Play）审核，审核通过才允许上架售卖

不同商店要不同的"包装规格"：
- iOS：只能从 App Store 分发，用 IPA 包
- Android：Google Play 要 AAB，其他渠道用 APK

两种主流安装包格式

格式 大白话 用途
IPA iOS 专用安装包 App Store / TestFlight
APK Android 传统安装包 直接安装、各应用市场
AAB Android 新版发布格式 仅 Google Play（更省空间）

对 iOS 工程师：这套流程你熟得不能再熟——Xcode Archive → 签名 → 上传 App Store Connect → TestFlight → 审核。Flutter 只是把"在 Xcode 里点按钮"换成了命令行 + 配置文件。

二、再讲"为什么"：为什么要签名、为什么审核？

环节 为什么必须有 大白话
签名 证明 App 是你的、没被篡改 防伪章，防止别人冒充你的 App
审核 保证 App 安全合规 市场监管，防病毒/违规内容
版本号管理 区分每一次发布 包装上的"批次号"，出问题能定位
TestFlight 上架前让测试人员/用户试用 先开"试吃会"，没问题再正式营业

签名的本质（大白话）：

你的开发者账号 = 一张"身份证"；签名 = 用你的私钥给 App 盖"电子章"。
用户安装时系统验证这个章：章是真的 → 允许装；章不对 → 拒绝装（防篡改）。

三、怎么用：打包上架全流程

3.1 打包前的准备（通用）

第一步：确认项目能正常构建

# 检查依赖
flutter pub get

# 本地跑一遍确认没问题
flutter run

# 跑测试（可选但推荐）
flutter test

第二步：检查 App 配置

# pubspec.yaml 里的版本号（先想好版本策略）
version: 1.0.0+1
# 含义：1.0.0 是"版本号"（用户看到），+1 是"构建号"（开发者用，必须递增）

3.2 iOS 打包流程（含签名）

前提准备（一次性的）：
1. 注册 Apple Developer 账号（$99/年）
2. 在 developer.apple.com 创建 App ID
3. 在 Xcode 里配置 Team（登录你的开发者账号）
4. 创建证书（Certificates）和描述文件（Profiles）——Xcode 现在大多自动管理（Automatically manage signing）

打包步骤：

# 1. 构建 iOS Release 包
flutter build ios --release

# 2. 打开 Xcode（产物在 build/ios/iphoneos/）
open ios/Runner.xcworkspace

然后在 Xcode 里（和你平时一模一样）：
1. 选择 Any iOS Device (arm64) 作为目标设备
2. 菜单：Product → Archive（归档）
3. Archive 完成后打开 Organizer（Window → Organizer）
4. 选 Distribute App → App Store Connect → Upload

或者用命令行（Fastlane 老熟人了）：

# 用 fastlane 上传（配置 Fastfile 后）
fastlane upload_testflight

签名相关常见报错（必看）：

报错 原因 解决
"No signing certificate found" 没配置证书 Xcode 登录账号 + Automatically manage signing
"Provisioning profile doesn't include this device" 真机调试缺设备 把设备 UDID 加进描述文件
"App ID 冲突" Bundle ID 已被占用 换一个唯一的 Bundle ID（如 com.xxx.todoapp）

对 iOS 工程师：这就是你平时 Xcode 的 Archive + Distribute 流程，Flutter 不改变任何签名逻辑，只是 flutter build ios 帮你把 Dart 代码编译好。

3.3 TestFlight 分发（上架前试吃）

大白话： TestFlight 是苹果官方的"试吃会"——把包上传后，测试人员（最多 10000 人）通过 TestFlight App 安装体验。

流程：
1. 上传包到 App Store Connect（上一步的 Upload 已搞定）
2. 打开 appstoreconnect.apple.com → 你的 App → TestFlight
3. 添加测试人员（邮箱或公开链接）
4. 测试人员在手机上装 TestFlight App → 接受邀请 → 安装测试版

TestFlight 小知识：
- 测试版有效期 90 天
- 可以分"内部测试组"（自己团队）和"外部测试组"（外部用户，需要 Beta App Review）
- TestFlight 审核 ≠ 上架审核：TestFlight 快，上架慢（一般 1-3 天）

3.4 App Store 上架避坑指南（重点）

上架步骤（App Store Connect 里填写）：
1. 新建 App（选 Bundle ID）
2. 填基本信息：名称、副标题、描述、关键词、分类
3. 上传截图（6.7/6.5/5.5 英寸等尺寸）
4. 填隐私政策网址（必填！）
5. 选"自动发布"或"手动发布"
6. 提交审核

避坑清单（高频被拒原因）：

坑 大白话 解决办法
缺少隐私政策 收集用户数据必须声明 准备隐私政策网页，App 内也要有链接
使用私有 API 调了苹果不允许的接口 检查代码，去掉私有 API
截图与实际不符 截图有功能实际没有 截图必须真实
需要登录才能看到核心功能 审核员进不去 App 提供审核专用演示账号
诱导评分 弹窗诱导用户打五星 去掉，改用合规评分组件
2.1 大礼包（账号问题） 账号异常或信息不全 补充公司信息、联系人、出口合规

审核时间： 一般 1-3 天；被拒后修改重新提交，别急着重复提交相同版本。

3.5 Android 打包（AAB 与上架）

前提准备：
1. 创建签名密钥（Keystore，类似 iOS 的证书）

# 生成密钥（一次性的，务必保存好！）
keytool -genkey -v -keystore ~/key.jks \
  -keyalg RSA -keysize 2048 -validity 10000 -alias upload
  1. 在 android/key.properties 配置密钥（注意别提交到 git！）
storePassword=你的密码
keyPassword=你的密码
keyAlias=upload
storeFile=/Users/you/key.jks
  1. 在 android/app/build.gradle 里配置签名（参考 Flutter 官方文档配置 signingConfigs）

打包命令：

# 1. 构建 AAB（Google Play 专用，更省空间）
flutter build appbundle --release
# 产物：build/app/outputs/bundle/release/app-release.aab

# 2. 构建 APK（直接安装 / 国内应用市场）
flutter build apk --release
# 产物：build/app/outputs/flutter-apk/app-release.apk

上传 Google Play：
1. 注册 Google Play 开发者账号（$25 一次性）
2. 在 Play Console 创建应用
3. 上传 AAB 文件
4. 填商品详情、内容评级（IARC 问卷）、隐私政策
5. 提交审核（Google 审核通常几小时-几天）

Android 常见坑：

坑 解决
签名密钥丢了 无法更新已上架 App！一定备份好 key.jks
版本号不递增 Google Play 拒绝相同版本号
64 位要求 新版 Flutter 默认支持，别手动关
国内渠道（华为/小米等） 各自要求不同，一般传 APK 或按要求传 AAB

3.6 版本管理（发布节奏）

大白话： 版本号是"App 的身份证批次"，管理好版本 = 知道每个用户用的哪版、出了问题能追溯。

版本号规则（语义化版本，SemVer）：

主版本.次版本.补丁版本
  1   .  2  .  3

主版本：大改（不兼容）→ 1.0.0 → 2.0.0
次版本：加功能（兼容）→ 1.0.0 → 1.1.0
补丁版本：修 bug → 1.0.0 → 1.0.1

发布策略（大白话）：

阶段 版本示例 说明
开发中 0.1.0 内部测试
内测 0.9.0 TestFlight / 内测群
正式发布 1.0.0 App Store / Google Play
修复 1.0.1 小修小补
大更新 1.1.0 / 2.0.0 加功能 / 重构

版本管理工具：
- Git 打 tag：git tag v1.0.0
- 变更日志（CHANGELOG.md）：记录每个版本改了什么（用户和审核都喜欢）
- pubspec 里的 version: 1.0.0+1 要和 Git tag 保持一致

四、iOS 开发者视角（老司机对照表）

iOS 原生 Flutter 大白话
Xcode Archive flutter build ios + Xcode Archive 归档
Code Signing（证书+描述文件） 同一套签名流程 签名
App Store Connect App Store Connect（一样） 上架后台
TestFlight TestFlight（一样） 试吃会
Xcode Organizer Organizer（一样） 管理归档
Info.plist 配置 pubspec + Info.plist 应用配置
iTunes Connect 审核 App Store 审核（一样） 审核
Fastlane deliver fastlane（通用） 自动化上传
gradle（Android 那边） flutter build appbundle Android 打包

给 iOS 工程师的真心话：
- iOS 打包上架流程和原生完全一样——还是 Xcode Archive、还是 App Store Connect、还是 TestFlight。你只是多了一步 flutter build ios。
- 你需要新学的主要是 Android 打包（签名密钥、AAB、Google Play），但对 iOS 老司机来说，概念全部对应：key.jks ≈ 证书，AAB ≈ IPA，Play Console ≈ App Store Connect。
- 版本号 1.0.0+1 里 +1 就是 iOS 的 Build Number，1.0.0 是 CFBundleShortVersionString，完全对应。

五、小节小结

  1. 打包 = 把代码做成安装包；签名 = 盖防伪章；上架 = 过审核。
  2. iOS：flutter build ios → Xcode Archive → 上传 App Store Connect → TestFlight 分发 → 提交审核。
  3. iOS 避坑：隐私政策、审核账号、截图真实、别诱导评分、别用私有 API。
  4. Android：生成 keystore → 配置签名 → flutter build appbundle（Google Play）/ flutter build apk（其他渠道）。
  5. Android 避坑：密钥一定备份（丢了无法更新）、版本号递增、64 位。
  6. 版本管理：语义化版本（主.次.补丁），Git tag + CHANGELOG 配合。

六、本节动手练习（含答案提示）

练习 1：格式选择

上架 Google Play 应该构建什么格式？想直接发 APK 给朋友安装呢？

✅ 答案提示：Google Play 用 AAB（flutter build appbundle，更省空间）；直接安装用 APK（flutter build apk）。

练习 2：签名理解

为什么签名密钥（keystore）丢失会出大问题？

✅ 答案提示：签名是 App 的"防伪章"，商店和系统靠它验证 App 是你的。密钥丢了就无法用同一身份发布更新，已上架的 App 只能下架重来。

练习 3：版本号

现在是 1.0.0，修了一个 bug 应该用什么版本号？加了一个大功能呢？

✅ 答案提示：修 bug → 1.0.1（补丁版本+1）；加大功能 → 1.1.0（次版本+1）。大重构不兼容才到 2.0.0。

练习 4：上架流程

iOS 上架到 App Store 的完整流程是什么（按顺序）？

✅ 答案提示：flutter build ios --release → Xcode 里 Archive → Organizer 里 Distribute 上传 App Store Connect → 填商品信息（名称/截图/隐私政策）→ 提交审核 → 审核通过发布。

练习 5：TestFlight 作用

TestFlight 和 App Store 正式上架有什么区别？

✅ 答案提示：TestFlight 是测试分发渠道（最多 1 万人、有效期 90 天、审核快），用于正式发布前让测试人员试用；App Store 正式上架要完整审核（1-3 天），面向所有用户。
