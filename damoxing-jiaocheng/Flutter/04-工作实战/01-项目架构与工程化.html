01-项目架构与工程化

大白话版 · 项目架构与工程化（小白向）
目标：搞懂目录结构规范、pubspec 依赖管理、多环境配置、代码规范与 lint、CI/CD 简介，以及状态管理在真实项目中的组合用法。

一、先讲"是什么"：工程化到底在解决什么问题？

一句话版本：工程化 = 一套让项目"多人协作不乱、长期维护不崩、自动发布不慌"的规范和工具。

打个比方：

一个项目就像一家餐厅的后厨：
- 目录结构规范 = 厨具分类摆放（锅放哪、调料放哪），新厨师来了不会找不到东西
- 依赖管理（pubspec） = 采购清单（要用哪些食材/供应商），统一登记、版本可控
- 多环境配置 = 同一套菜谱，在"试菜间"和"正式大堂"用不同的火候参数
- 代码规范 + lint = 厨师着装和操作规范，大家写得像一个人写的
- CI/CD = 自动化的"流水线"：菜做好自动质检、自动打包上桌

大白话结论： 单机小 Demo 不需要工程化；一旦要上线、要团队协作，工程化就是救命稻草。

二、再讲"为什么"：不工程化会怎样？

问题 不工程化的后果
目录乱 新同事找不到文件，代码重复堆叠
依赖乱 直接改 pubspec 版本，一升级全崩，没人知道改了什么
环境不分 测试环境接口和正式环境接口混用，上线事故
不规范 10 个人 10 种写法，review 地狱
没 CI 每次发布手动跑测试、手动打包，漏一步就出 bug

对 iOS 工程师：这一整套思路和你在 Xcode 里维护工程、用 CocoaPods/SwiftPM 管依赖、用 Fastlane 自动化发布是一模一样的，只是工具换成了 Flutter 生态的。

三、怎么用：六大块逐个击破

3.1 目录结构规范（推荐分层）

大白话： 把代码按"职责"分房间，而不是按"类型"堆一起。

推荐的分层目录（真实项目常用）：

lib/
├── main.dart                  # 入口：启动 App、初始化
├── app.dart                   # 根 Widget（MaterialApp、主题、路由表）
├── core/                      # 核心基础设施（不依赖业务）
│   ├── constants/             # 常量（颜色、字符串、接口地址）
│   ├── theme/                 # 主题（亮色/暗色）
│   ├── network/               # 网络层（dio 封装）
│   ├── storage/               # 本地存储封装
│   └── utils/                 # 工具函数
├── features/                  # 按业务功能分模块（重点）
│   ├── todo/                  # 待办功能
│   │   ├── data/              # 数据层（模型、API、本地存储）
│   │   ├── domain/            # 业务逻辑（仓库、用例）
│   │   └── presentation/      # 界面层（页面、状态管理、组件）
│   ├── weather/               # 天气功能（同样三层）
│   └── ...
├── shared/                    # 跨模块共享组件
│   └── widgets/               # 通用组件（按钮、空态、加载态）
└── router/                    # 路由配置

三层架构（data / domain / presentation）大白话：

层 是什么 大白话
presentation 界面 + 状态 前台服务员：接待客人（展示 UI）
domain 业务规则 店长：定规矩（下单逻辑）
data 数据来源 仓库管理员：进货出货（网络/数据库）

铁律： 上层可以依赖下层，下层绝不能依赖上层（界面不能直接写死数据库逻辑）。

3.2 依赖管理（pubspec.yaml ≈ 你的 Podfile）

大白话： pubspec.yaml 是 Flutter 项目的"采购清单"，记录项目用什么依赖、什么版本。

name: todo_app            # 项目名（包名基础）
description: 待办清单示例
publish_to: 'none'        # 不发布到 pub.dev
version: 1.0.0+1          # 版本号：1.0.0 是版本，+1 是构建号

environment:
  sdk: '>=3.0.0 <4.0.0'   # Dart SDK 版本范围

dependencies:             # 正式依赖（发布要用）
  flutter:
    sdk: flutter
  dio: ^5.4.0             # ^5.4.0：允许 5.x 的最新版，不允许跨大版本
  provider: ^6.1.0
  shared_preferences: ^2.2.0   # 本地存储

dev_dependencies:         # 开发依赖（只测试/工具用，不打进包）
  flutter_test:
    sdk: flutter
  flutter_lints: ^4.0.0   # 代码规范检查

flutter:                  # Flutter 专属配置
  uses-material-design: true
  assets:                 # 资源文件（图片、字体）
    - assets/images/

常用命令（背下来）：

命令 作用 大白话
flutter pub get 根据 pubspec 下载依赖 按清单采购
flutter pub add dio 添加依赖并自动写进 pubspec 直接在清单加一行
flutter pub upgrade 升级依赖 换新供应商
flutter pub outdated 查看哪些依赖有新版 检查库存是否过时

版本号语法（^ 的意思）： ^5.4.0 = "5.4.0 及以上，但不超过 6.0.0"（大版本不变）。大版本升级通常有破坏性变更，要谨慎。

对 iOS 工程师：pubspec ≈ Podfile + Package.swift，flutter pub get ≈ pod install。区别是 Flutter 自带依赖解析，不用管 xcworkspace。

3.3 多环境配置（dev / prod）

大白话： 同一套代码，在开发（dev）和正式（prod）环境用不同的配置（接口地址、App 名称、日志开关）。

实现方式一：dart-define（最简单，推荐）

# 启动开发环境
flutter run --dart-define=ENV=dev --dart-define=API_BASE=https://dev.example.com

# 启动正式环境
flutter run --dart-define=ENV=prod --dart-define=API_BASE=https://api.example.com

// 代码里读取配置
class AppConfig {
  static const String env = String.fromEnvironment('ENV', defaultValue: 'dev');
  static const String apiBase = String.fromEnvironment(
    'API_BASE',
    defaultValue: 'https://dev.example.com',
  );

  static bool get isProd => env == 'prod';
  static bool get isDebug => kDebugMode;  // 是否调试模式
}

// 使用
// final client = Dio(BaseOptions(baseUrl: AppConfig.apiBase));

实现方式二：环境文件（进阶，多个复杂配置时）

在项目根目录建 env/dev.json、env/prod.json，启动时传入：

flutter run --dart-define=ENV_FILE=assets/env/dev.json

环境配置要点：
1. 接口地址分 dev/prod
2. 日志：dev 全开，prod 关闭或只留错误
3. App 名称/图标：dev 可加"测试"后缀区分
4. 测试开关：dev 可一键进测试账号

对 iOS 工程师：≈ Xcode 的 Debug/Release Configuration + xcconfig 文件，--dart-define 就是 Flutter 版的环境变量注入。

3.4 代码规范与 lint

大白话： lint 是"自动纠察队"，帮你检查代码是否符合规范，问题一目了然。

Flutter 项目自带 lint：

# pubspec.yaml 里已配好
dev_dependencies:
  flutter_lints: ^4.0.0

使用：

# 检查代码规范
flutter analyze

# 自动修复能修的问题
dart fix --apply

常见规范（小白先记住这 5 条）：
1. 类名用大驼峰（TodoItem），变量/方法用小驼峰（itemCount）
2. 常量用下划线大写（kMaxItems）
3. 私有成员加下划线（_controller）
4. 能 const 就 const
5. import 排序、不要有未使用的变量

对 iOS 工程师：flutter analyze ≈ Xcode 的 Analyze + SwiftLint；dart fix --apply ≈ 自动修复警告。团队可加 analysis_options.yaml 自定义规则，就像 .swiftlint.yml。

3.5 CI/CD 简介（自动流水线）

大白话： CI/CD 是"自动工厂"：代码一提交，自动跑测试、自动检查、自动打包、自动分发。

术语 全称 大白话
CI Continuous Integration 持续集成 每次提交代码自动跑检查+测试，有问题立刻报警
CD Continuous Delivery 持续交付 自动打包、自动发布到测试/商店

常见 CI/CD 工具（Flutter 生态）：

工具 大白话
GitHub Actions GitHub 自带的自动化流水线（最常用、免费额度够用）
GitLab CI GitLab 内置 CI
Codemagic 专门优化 Flutter 的云打包服务
Fastlane iOS/Android 通用的自动化发布工具（iOS 老熟人）

一个极简 GitHub Actions 示例：

# .github/workflows/flutter_ci.yml
name: Flutter CI

on:
  push:            # 每次 push 触发
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: subosito/flutter-action@v2   # 装 Flutter
        with:
          flutter-version: '3.x'
      - run: flutter pub get               # 拉依赖
      - run: flutter analyze               # 代码检查
      - run: flutter test                  # 跑测试

大白话流程： 你 push 代码 → GitHub 自动开一台机器 → 装 Flutter → 拉依赖 → 检查代码 → 跑测试 → 全绿才算通过。

对 iOS 工程师：CI/CD ≈ Fastlane + Xcode Cloud 的组合，只是配置文件是 YAML 而不是 Ruby/Swift 脚本。

3.6 状态管理在真实项目中的组合用法

大白话： 真实项目里不是只用一种状态管理，而是"组合拳"：

场景 用什么 为什么
页面内局部状态 setState 简单直接，页面自己管
跨页面共享的少量状态（登录态/主题） Provider（ChangeNotifier） 轻量、易上手
复杂业务状态（购物车/订单流） Riverpod 或 Bloc 可测试、可追踪
异步数据流（实时数据） StreamBuilder / Riverpod stream 响应式数据
路由/导航 交给 Navigator / go_router 不进状态管理

一个组合示例（Provider 管理全局 + 页面局部 setState）：

// 1. 全局状态：登录状态（ChangeNotifier）
class AuthModel extends ChangeNotifier {
  bool _isLoggedIn = false;
  bool get isLoggedIn => _isLoggedIn;

  void login() {
    _isLoggedIn = true;
    notifyListeners();   // 通知所有监听者刷新
  }

  void logout() {
    _isLoggedIn = false;
    notifyListeners();
  }
}

// 2. main.dart 里用 ChangeNotifierProvider 提供全局状态
// ChangeNotifierProvider(
//   create: (_) => AuthModel(),
//   child: const MyApp(),
// )

// 3. 页面里读取/使用全局状态 + 页面局部 setState
class HomePage extends StatefulWidget {
  const HomePage({super.key});
  @override
  State<HomePage> createState() => _HomePageState();
}

class _HomePageState extends State<HomePage> {
  int _localCount = 0;  // 页面局部状态，用 setState 管

  @override
  Widget build(BuildContext context) {
    // 读全局状态：登录了吗？
    final auth = context.watch<AuthModel>();

    return Scaffold(
      appBar: AppBar(title: const Text('组合用法')),
      body: Center(
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            Text(auth.isLoggedIn ? '已登录' : '未登录'),
            const SizedBox(height: 12),
            Text('局部计数：$_localCount'),
            const SizedBox(height: 12),
            ElevatedButton(
              onPressed: () => setState(() => _localCount++),  // 局部用 setState
              child: const Text('局部 +1'),
            ),
            ElevatedButton(
              onPressed: auth.isLoggedIn ? auth.logout : auth.login,  // 全局用 Provider
              child: Text(auth.isLoggedIn ? '退出登录' : '登录'),
            ),
          ],
        ),
      ),
    );
  }
}

选型口诀（真实项目）：

小项目：setState + Provider 就够。
中项目：Provider/Riverpod 按模块划分。
大项目：Riverpod 或 Bloc + 分层架构。
先跑起来，别过度设计；架构为业务服务，不为了炫技。

iOS 原生 Flutter 大白话
Xcode 工程目录（Groups） lib/ 目录分层 项目组织

给 iOS 工程师的真心话：
- pubspec 就是"Podfile + Package.swift 二合一"，flutter pub get 就是 pod install，上手零成本。
- --dart-define 就是 xcconfig 环境变量，Swift 里 Environment 那套。
- CI/CD 你玩过 Fastlane 的话，GitHub Actions 的 YAML 只是换个写法。
- 状态管理：ChangeNotifier ≈ ObservableObject，context.watch ≈ @ObservedObject 的订阅，概念直接平移。

五、小节小结

  1. 工程化解决"多人协作不乱、长期维护不崩、自动发布不慌"。
  2. 目录结构：按职责分层（core / features / shared），功能内再分 data / domain / presentation。
  3. pubspec.yaml 管理依赖：^ 控制版本范围，flutter pub get 拉依赖。
  4. 多环境：--dart-define 注入 dev/prod 配置（接口地址、日志、App 名）。
  5. lint：flutter analyze 检查 + dart fix --apply 自动修。
  6. CI/CD：GitHub Actions 自动化跑检查+测试+打包。
  7. 状态管理组合拳：局部 setState + 全局 Provider + 复杂场景 Riverpod/Bloc。

六、本节动手练习（含答案提示）

练习 1：目录判断

一个"用户头像组件"应该放在哪个目录？为什么？

✅ 答案提示：放 shared/widgets/（跨模块通用组件）。因为它被多个功能模块复用，不属于某个具体业务。

练习 2：版本号理解

dio: ^5.4.0 表示允许什么版本？

✅ 答案提示：允许 5.4.0 及以上、但小于 6.0.0 的版本（大版本 5 不变，小版本可更新）。

练习 3：环境配置

想让 App 在正式环境不打印调试日志，应该怎么做？

✅ 答案提示：用 AppConfig.isProd（来自 --dart-define=ENV=prod）判断，正式环境把 logger 级别调成 error 或关闭；也可配合 kDebugMode 判断。

练习 4：CI 流程

一个最简单的 Flutter CI 流程，按顺序应该做哪几步？

✅ 答案提示：checkout 代码 → 装 Flutter → flutter pub get → flutter analyze → flutter test（全绿才通过）。

练习 5：状态管理选型

一个中大型项目，登录状态要跨页面共享、购物车逻辑复杂。分别适合用什么？

✅ 答案提示：登录状态用 Provider（简单共享）；购物车等复杂业务逻辑用 Riverpod 或 Bloc（可测试、可追踪）。
