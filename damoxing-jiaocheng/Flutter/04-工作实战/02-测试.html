02-测试

大白话版 · Flutter 测试实战（小白向）
目标：学会单元测试、Widget 测试、集成测试、mock 依赖、常见测试套路与覆盖率。

一、先讲"是什么"：测试到底在测什么？

一句话版本：测试 = 用代码验证"代码没写错"，分三层：测逻辑、测界面、测整体流程。

打个比方（餐厅质检）：

  • 单元测试 = 单独检查"切菜师傅"：给一把菜、一把刀，验证切出来的丝是不是粗细均匀（只测一个函数/一个类）
  • Widget 测试 = 检查"一道菜上桌"：摆盘对不对、菜名对不对（测一个界面组件）
  • 集成测试 = 完整走一遍"客人从进门到结账"：全流程一起跑（测整个 App 流程）

Flutter 三种测试对比

类型 大白话 运行速度 场景
单元测试 只测一个函数/类 极快（毫秒级） 工具函数、Model 解析、业务逻辑
Widget 测试 测一个界面组件 快（秒级） 按钮点击、文案显示、交互
集成测试 整个 App 流程 慢（分钟级） 登录→首页→下单 全链路

测试金字塔（记住这个形状）：

        /\       集成测试（少，最贵）
       /  \
      /----\     Widget 测试（中）
     /------\
    /--------\   单元测试（多，最便宜，主力）

大白话： 大部分测试应该是最便宜的单元测试，界面和集成测试少而精。

二、再讲"为什么"：为什么要写测试？

理由 大白话
防止回归 改 A 功能把 B 搞坏了？测试立刻报警
敢重构 有测试兜底，随便改代码不怕
文档作用 测试展示了"这个函数应该怎么用、返回什么"
面试加分 大厂几乎必问测试
CI 自动质检 提交代码自动跑测试，坏代码进不了主干

对 iOS 工程师：这和 XCTest / ViewInspector 的定位完全一样：单元测试 ≈ XCTest 的 testXxx()，Widget 测试 ≈ 用 ViewInspector 断言 SwiftUI 视图。

三、怎么用：四类测试逐个击破

3.1 单元测试（测逻辑，最快最常用）

场景： 测一个计算函数和 Model 解析。

// 被测代码（lib/utils/calculator.dart）
class Calculator {
  int add(int a, int b) => a + b;

  // 计算总价：满 100 减 20
  int totalPrice(int price, int count) {
    final total = price * count;
    return total >= 100 ? total - 20 : total;
  }
}

// 测试代码（test/calculator_test.dart）
import 'package:flutter_test/flutter_test.dart';
import 'package:todo_app/utils/calculator.dart';

void main() {
  group('Calculator 计算器', () {       // group：分组，方便看结果
    test('加法：2 + 3 = 5', () {
      final calc = Calculator();
      expect(calc.add(2, 3), 5);       // expect：断言（期望等于 5）
    });

    test('总价满 100 减 20', () {
      final calc = Calculator();
      expect(calc.totalPrice(30, 4), 100);   // 120 - 20 = 100
      expect(calc.totalPrice(30, 2), 60);    // 不满 100，不优惠
    });

    test('边界：正好 100 也要优惠', () {
      final calc = Calculator();
      expect(calc.totalPrice(25, 4), 80);    // 100 - 20 = 80
    });
  });
}

运行单元测试：

flutter test test/calculator_test.dart
# 或者全部测试
flutter test

核心 API 速记：

API 作用
test('描述', () {...}) 定义一条测试
group('描述', () {...}) 分组
expect(实际值, 期望值) 断言：相等
expect(() => fn(), throwsException) 断言：抛异常

测试套路（AAA 模式）：
1. Arrange（准备）：创建对象、准备数据
2. Act（执行）：调用被测函数
3. Assert（断言）：检查结果

3.2 Widget 测试（测界面）

场景： 测一个计数器页面：点击按钮，数字 +1。

// 被测页面（lib/counter_page.dart）
class CounterPage extends StatefulWidget {
  const CounterPage({super.key});
  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  int _count = 0;

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(
        child: Column(
          mainAxisAlignment: MainAxisAlignment.center,
          children: [
            Text('计数：$_count', key: const Key('count_text')),  // 加 key 方便测试找
            ElevatedButton(
              key: const Key('add_button'),
              onPressed: () => setState(() => _count++),
              child: const Text('+1'),
            ),
          ],
        ),
      ),
    );
  }
}

// 测试代码（test/counter_page_test.dart）
import 'package:flutter/material.dart';
import 'package:flutter_test/flutter_test.dart';
import 'package:todo_app/counter_page.dart';

void main() {
  testWidgets('点击按钮计数 +1', (WidgetTester tester) async {
    // 1. 把页面"铺"到测试环境里
    await tester.pumpWidget(const MaterialApp(home: CounterPage()));

    // 2. 初始状态：计数为 0
    expect(find.text('计数：0'), findsOneWidget);

    // 3. 点击 +1 按钮
    await tester.tap(find.byKey(const Key('add_button')));

    // 4. 刷新一帧（setState 后需要 pump）
    await tester.pump();

    // 5. 断言：现在显示 1
    expect(find.text('计数：1'), findsOneWidget);
  });
}

Widget 测试核心 API：

API 作用 大白话
testWidgets('描述', (tester) async {...}) 定义 Widget 测试 开一个小舞台
tester.pumpWidget(widget) 把组件放上舞台 摆道具
tester.tap(finder) 模拟点击 用手指点
tester.pump() 刷新一帧 让画面更新
find.text('xxx') 按文本找组件 找带字的元素
find.byKey(Key('xxx')) 按 key 找组件 找贴标签的元素
findsOneWidget / findsNothing 断言找到 1 个 / 0 个 检查有没有

找组件的三种常用方式：

find.text('计数：1')          // 按文字
find.byKey(const Key('add_button'))  // 按 key（推荐，稳定）
find.byType(ElevatedButton)   // 按类型

3.3 mock 依赖（模拟网络/外部服务）

大白话： 测试时不想真的发网络请求（又慢又不可控），就用"假接口"（mock）模拟返回。

场景： 测一个"获取用户信息"的业务函数，mock 网络层。

// 被测代码（lib/services/user_service.dart）
class UserService {
  final ApiClient api;   // 网络客户端

  UserService(this.api);

  Future<String> getUserName(int id) async {
    final data = await api.get('/user/$id');
    return data['name'] as String;
  }
}

// 测试代码（test/user_service_test.dart）
import 'package:flutter_test/flutter_test.dart';
import 'package:todo_app/services/user_service.dart';

// 手写一个"假 ApiClient"（不用任何 mock 库也能做）
class FakeApiClient implements ApiClient {
  @override
  Future<Map<String, dynamic>> get(String path) async {
    // 不发网络请求，直接返回假数据
    if (path == '/user/1') {
      return {'name': '小明'};
    }
    throw Exception('404');
  }
}

void main() {
  test('获取用户名成功', () async {
    final service = UserService(FakeApiClient());  // 注入假客户端
    final name = await service.getUserName(1);
    expect(name, '小明');
  });

  test('获取用户名失败抛异常', () async {
    final service = UserService(FakeApiClient());
    expect(() => service.getUserName(999), throwsException);
  });
}

用 mockito（业界标准库）更省事：

// 需要先 flutter pub add mockito dev:build_runner
// 生成 mock 类后：
// final mockApi = MockApiClient();
// when(mockApi.get('/user/1')).thenAnswer((_) async => {'name': '小明'});

mock 的原则：
1. 只 mock 外部依赖（网络、数据库、系统服务），别 mock 自己写的业务逻辑（不然测试就没意义了）。
2. 依赖要能"注入"：构造函数传进去（依赖注入），这样才能在测试里换假的。

3.4 集成测试（全流程）

场景： 整个 App 从首页走到详情页，验证真实流程。

// 集成测试（integration_test/app_test.dart）
// 需要在 pubspec 加 integration_test 依赖：
// dev_dependencies:
//   integration_test:
//     sdk: flutter

import 'package:flutter_test/flutter_test.dart';
import 'package:integration_test/integration_test.dart';
import 'package:todo_app/main.dart' as app;

void main() {
  IntegrationTestWidgetsFlutterBinding.ensureInitialized();

  testWidgets('完整流程：打开 App → 点按钮 → 看到结果', (tester) async {
    app.main();                                  // 启动真实 App
    await tester.pumpAndSettle();                // 等动画/加载完成

    // 在真实 App 上操作
    await tester.tap(find.text('开始'));
    await tester.pumpAndSettle();

    expect(find.text('成功'), findsOneWidget);
  });
}

运行集成测试（需要真机/模拟器）：

flutter test integration_test/app_test.dart -d <device_id>

注意： 集成测试慢、依赖真实环境，别写太多，只覆盖核心用户路径。

3.5 测试覆盖率

大白话： 覆盖率 = "被测代码行数 / 总代码行数"，看测试漏了哪里。

# 跑测试并生成覆盖率报告
flutter test --coverage

# 报告在 coverage/lcov.info，可用工具可视化
# 或直接看终端汇总（有些工具会输出百分比）

覆盖率不是越高越好（重点）：
- 核心业务逻辑覆盖率要尽量高（>80%）
- UI 纯展示代码不必强求
- 比覆盖率更重要的是：关键路径测到位（登录、支付、数据解析这些出问题就完蛋的）

测试套路总结（背下来）：
1. AAA：准备 → 执行 → 断言
2. 只测"行为"，不测"实现细节"
3. 一个测试只验证一件事
4. 描述要清晰：'点击登录按钮后显示加载中'
5. mock 外部依赖，别发真网络请求

四、iOS 开发者视角（老司机对照表）

iOS 原生 Flutter 大白话
XCTest testXxx() test('...', () {...}) 单元测试
XCTAssertEqual expect(实际, 期望) 断言
ViewInspector（SwiftUI） testWidgets + find Widget 测试
tester.tap ≈ XCUITest tap tester.tap 模拟点击
XCTestCase setUp/tearDown setUp/tearDown 测试准备清理
OCMock / Mockingbird mockito / Fake 类 mock 依赖
XCUITest 全流程 integration_test 集成测试
xccov 覆盖率 flutter test --coverage 覆盖率
Fastlane scan / Xcode Cloud CI 里跑 flutter test 自动测试

给 iOS 工程师的真心话：
- 单元测试：test + expect 就是 XCTest 的 testXxx + XCTAssert，写法更轻。
- Widget 测试：比 ViewInspector 更直观——find.text('xxx') 找元素、tester.tap 点击，非常像 XCUITest 但跑得快得多（不需要模拟器）。
- mock：iOS 用协议注入 + Mockingbird，Flutter 用接口注入 + mockito，思路一模一样（都靠依赖注入）。
- 关键差异：Flutter 的 Widget 测试速度极快（毫秒级），可以写很多；iOS 的 UI 测试很慢，只能少写。所以 Flutter 项目测试金字塔的"中腰"特别肥。

五、小节小结

  1. 三层测试：单元（测逻辑）、Widget（测界面）、集成（测全流程）。
  2. 测试金字塔：单元测试最多最便宜，集成测试少而精。
  3. 单元测试：test + group + expect，AAA 套路（准备→执行→断言）。
  4. Widget 测试：testWidgets + pumpWidget + find + tap + pump。
  5. mock：用假对象代替网络/数据库等外部依赖，靠依赖注入实现。
  6. 集成测试：integration_test 跑真实 App 全流程，覆盖核心路径即可。
  7. 覆盖率：核心逻辑 >80%，关键路径比数字更重要。

六、本节动手练习（含答案提示）

练习 1：选测试类型

以下场景分别用什么测试？
A. 验证一个"满减计算"函数　B. 验证登录页点击按钮跳转　C. 验证从登录到下单的完整流程

✅ 答案提示：A 单元测试（纯函数）；B Widget 测试（界面交互）；C 集成测试（全流程）。

练习 2：找 API

Widget 测试里，点击按钮后界面变了，为什么需要 tester.pump()？

✅ 答案提示：setState 触发重建需要刷新一帧才能看到新界面，pump() 就是"刷新一帧"；异步动画/网络完成用 pumpAndSettle() 等所有帧稳定。

练习 3：mock 判断

测试一个调用了 FirebaseAuth 的登录函数，应不应该发真实请求？怎么做？

✅ 答案提示：不应该发真实请求（不可控、慢、可能失败）。把 auth 依赖注入到构造函数，测试时传入 mock 假实现返回固定结果。

练习 4：断言

想验证"页面上没有'加载中'三个字"，用哪个断言？

✅ 答案提示：expect(find.text('加载中'), findsNothing);

练习 5：覆盖率理解

团队规定覆盖率要 100%，这个要求合理吗？为什么？

✅ 答案提示：不合理。纯展示代码、防御代码等难以覆盖，且高覆盖率不等于测到关键路径；合理做法是核心业务逻辑高覆盖 + 关键路径全覆盖。
