02-状态管理

大白话版 · 状态管理从入门到选型（小白向）
目标：搞懂"状态"是什么、setState 怎么用、为什么需要状态管理库，以及 Provider / Riverpod / Bloc 怎么选。

一、先讲"是什么"：状态到底是什么？

一句话版本：状态（State）= 会影响界面显示的数据。状态变了，界面就要跟着变。

打个比方：

你开了一家奶茶店，门口挂着一块电子招牌：
- 招牌上显示"今日特价：珍珠奶茶 8 元" —— 这就是状态（数据）
- 今天老板决定改成"买一送一" —— 你改招牌上的内容，客人看到的就是新信息
- 改招牌这个动作 = 更新状态；客人看到新内容 = 界面刷新

在 App 里：登录状态、购物车数量、点赞数、网络加载中/成功/失败……这些都是状态。

状态的两种"性格"

类型 说明 例子 大白话
局部状态 只属于某个页面/组件 计数器、开关、输入框文字 只在这一个房间里的东西
全局状态 多个页面/组件都要用 用户登录信息、主题色、购物车 整个房子共用的东西
  • 局部状态：setState 就够用。
  • 全局状态：需要"状态管理方案"（Provider / Riverpod / Bloc）。

二、再讲"为什么"：为什么需要状态管理？

2.1 先看 setState 的"能力边界"

setState 只能更新自己所在的 State 类里的界面。如果两个页面（甚至两个 Widget）要共享同一份数据，setState 就尴尬了：

没有状态管理的痛苦（大白话）：

你想让"购物车页面"和"商品列表页面"都显示购物车数量。
用 setState 的话，你得手动把数据一层层传下去（这叫状态提升），还要一层层回调回来。
页面一多，传参像"传纸条"一样绕来绕去，代码又臭又长，改一处崩三处。

状态管理库解决什么：

把"共享数据"放到一个"公共储物柜"（全局 store / provider）里。
谁想读，直接从柜子里拿；谁想改，改完柜子自动通知所有"关注的人"刷新。
就像公司的公共公告栏：HR 贴一张新通知，全公司的人都看得到。

2.2 状态提升（State Lifting）—— 先学这个，再学库

状态提升：把子组件里的状态"往上提"到父组件，由父组件统一管理，再通过参数传给子组件。

// 子组件：只负责"显示"数字（无状态）
class CounterDisplay extends StatelessWidget {
  final int count;           // 数据从外面传进来
  const CounterDisplay({super.key, required this.count});

  @override
  Widget build(BuildContext context) {
    return Text('当前计数：$count', style: const TextStyle(fontSize: 24));
  }
}

// 父组件：负责"管理"状态（有状态）
class CounterPage extends StatefulWidget {
  const CounterPage({super.key});
  @override
  State<CounterPage> createState() => _CounterPageState();
}

class _CounterPageState extends State<CounterPage> {
  int _count = 0;   // 状态提升到父组件这里

  void _add() {
    setState(() => _count++);   // 父组件更新状态
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: Center(
        child: Column(
          children: [
            CounterDisplay(count: _count),   // 数据传给子组件显示
            ElevatedButton(onPressed: _add, child: const Text('+1')),
          ],
        ),
      ),
    );
  }
}

大白话理解状态提升：

数字"住"在爸爸（父组件）家里，儿子（子组件）只负责"看"（展示）。
爸爸负责"记"（管理状态）和"改"（setState）。儿子需要看的时候，爸爸把数字告诉他。
好处：数据只在一个地方改，逻辑清晰；坏处：层级深了传参很烦——所以有了状态管理库。

三、怎么用：三大状态管理方案对比与选型

3.1 Provider（最推荐入门，官方认可）

大白话： Provider 就是一个"公共储物柜"。你把数据放进去，任何组件都能"伸手拿"，数据变了自动通知使用它的组件刷新。

  • 类比 iOS：Provider ≈ SwiftUI 的 ObservableObject + @EnvironmentObject，或 UIKit 里的"单例 + 通知"。
  • 核心 API 就 3 个：ChangeNotifier（会通知的类）、ChangeNotifierProvider（提供数据的柜子）、context.watch/read（拿数据）。
// 第一步：定义一个"会通知"的数据类
import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

class CartModel extends ChangeNotifier {
  int _count = 0;
  int get count => _count;

  void add() {
    _count++;
    notifyListeners();  // 通知所有"关注者"：数据变了，去刷新！
  }
}

void main() {
  runApp(
    // 第二步：把数据放进"柜子"（Provider）
    ChangeNotifierProvider(
      create: (_) => CartModel(),
      child: const MyApp(),
    ),
  );
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});
  @override
  Widget build(BuildContext context) {
    return MaterialApp(home: const CartPage());
  }
}

class CartPage extends StatelessWidget {
  const CartPage({super.key});

  @override
  Widget build(BuildContext context) {
    // 第三步：watch = "盯着看"，数据一变自动重建
    final cart = context.watch<CartModel>();

    return Scaffold(
      appBar: AppBar(title: const Text('购物车')),
      body: Center(
        child: Column(
          children: [
            Text('购物车里有 ${cart.count} 件商品', style: const TextStyle(fontSize: 24)),
            ElevatedButton(
              onPressed: () => context.read<CartModel>().add(),  // read = 只读不改界面
              child: const Text('加一件'),
            ),
          ],
        ),
      ),
    );
  }
}

记住一句话：watch 是"盯着看，变了就刷新"，read 是"拿一下就走，不刷新"。

3.2 Riverpod（Provider 的升级版，更现代）

大白话： Riverpod 是 Provider 的作者开发的"改良版"。它解决了 Provider 的一些痛点（比如编译期报错、测试麻烦），写法更安全。

  • 核心概念：用全局的 Provider / StateNotifierProvider 定义数据，组件通过 ref.watch 获取。
  • 类比 iOS：比 ObservableObject 更接近"依赖注入 + 响应式"的混合体。
// Riverpod 简版示例（了解风格即可，细节不用背）
import 'package:flutter_riverpod/flutter_riverpod.dart';

// 定义全局状态
final countProvider = StateProvider<int>((ref) => 0);

// 组件要继承 ConsumerWidget 才能用 ref
class CounterPage extends ConsumerWidget {
  @override
  Widget build(BuildContext context, WidgetRef ref) {
    final count = ref.watch(countProvider);  // 盯着看
    return Scaffold(
      body: Center(
        child: Text('计数：$count'),
      ),
    );
  }
}

Provider vs Riverpod（大白话对比）：

维度 Provider Riverpod
学习难度 低（入门首选） 中
编译期安全 一般（运行时才报错） 高（编译期就发现错误）
测试 麻烦一点 很方便
生态成熟度 非常成熟 快速增长
适合谁 新手、中小项目 追求类型安全的团队

3.3 Bloc（最重最规范，大型项目用）

大白话： Bloc 把状态管理变成"流水线"：界面发一个"事件"（Event）→ Bloc 处理逻辑 → 产出新"状态"（State）→ 界面刷新。数据流向是单向的，非常清晰，但样板代码多。

  • 类比 iOS：Bloc ≈ MVVM + Combine 的严格版，或者说像 Redux 的单向数据流。
  • 核心三件套：Event（发生了什么）、State（界面长啥样）、Bloc（大脑：事件 → 新状态）。
// Bloc 简版示例（了解流程即可）
// 事件：用户点了 +1
class AddEvent {}

// 状态：当前的计数
class CountState {
  final int count;
  CountState(this.count);
}

// Bloc：大脑，接收事件，产出新状态
class CounterBloc extends Bloc<AddEvent, CountState> {
  CounterBloc() : super(CountState(0)) {
    on<AddEvent>((event, emit) {
      emit(CountState(state.count + 1));  // 新状态 = 旧状态 + 1
    });
  }
}

// 界面上：把事件"送进" Bloc，界面自动监听状态刷新
// context.read<CounterBloc>().add(AddEvent());
// 用 BlocBuilder 监听状态变化自动重建界面

Bloc 的优缺点（大白话）：
- 优点：逻辑和界面完全分离，代码规范、可测试、大型团队协作友好。
- 缺点：样板代码多（一个功能要写 Event/State/Bloc 三个类），小项目用起来"杀鸡用牛刀"。

3.4 选型建议（直接抄作业）

项目规模 推荐方案 理由
练手项目 / 小 Demo setState + 状态提升 最简单，够用就行
中小型商业项目 Provider 上手快、生态成熟、够用
中型以上、追求安全 Riverpod 类型安全、测试方便
大型项目 / 团队协作 Bloc 规范强、职责清晰
已有 iOS 经验 都行，但建议从 Provider 入门 概念接近 ObservableObject，最顺

大白话结论：新手无脑先学 Provider，理解"柜子 + 通知"思想后，其他方案都是它的变体或加强版。

四、iOS 开发者视角（老司机对照表）

iOS 概念 Flutter 对应 大白话
@Published + ObservableObject ChangeNotifier + notifyListeners() 数据变化通知
SwiftUI @EnvironmentObject Provider 的 Provider.of / watch 从环境取共享数据
SwiftUI @State StatefulWidget + setState 局部状态
单例 + 通知中心 简单的全局 Provider 全局共享
Combine 的 sink context.watch 自动订阅 订阅数据流
MVVM 的 ViewModel ChangeNotifier 类（Provider） 界面逻辑承载者
Redux / TCA Bloc 单向数据流架构
依赖注入 Provider / Riverpod 的 create 注入共享依赖

给 iOS 工程师的真心话：
- Provider 的 ChangeNotifier 就是 SwiftUI 的 ObservableObject，notifyListeners() 就是 objectWillChange.send()，几乎 1:1 对应。
- Bloc 的单向数据流（Event → State → UI）和 TCA（The Composable Architecture）的思路很像，如果你用过 TCA，理解 Bloc 无压力。
- 别纠结"哪个最好"，能解决问题的就是好方案，小项目先用 Provider 跑起来。

五、小节小结

  1. 状态 = 影响界面的数据；局部状态用 setState，全局状态用状态管理库。
  2. 状态提升：把数据提到父组件统一管理，再传下去，是最朴素的共享方式。
  3. Provider：入门首选，"公共储物柜"思想，watch 盯着看自动刷新。
  4. Riverpod：Provider 升级版，更安全、更好测试。
  5. Bloc：单向数据流，规范强、代码多，适合大型项目。
  6. 选型：小项目 setState → 中项目 Provider → 大型项目 Bloc/Riverpod。

六、本节动手练习（含答案提示）

练习 1：判断状态类型

下面哪些属于"局部状态"，哪些属于"全局状态"？
A. 登录用户名　B. 输入框里的文字　C. 购物车总价　D. 开关是否打开

✅ 答案提示：全局：A、C（多个页面要用）；局部：B、D（只在一个页面用）。

练习 2：setState 与 Provider

一句话说清：什么时候用 setState 就够了？什么时候必须上状态管理库？

✅ 答案提示：状态只影响当前页面（局部）时用 setState；状态要被多个页面/组件共享（全局）时用状态管理库（Provider 等）。

练习 3：watch vs read

Provider 里 context.watch<T>() 和 context.read<T>() 有什么区别？

✅ 答案提示：watch 会订阅数据变化，数据变了自动重建当前组件；read 只读取一次，不订阅、不触发重建。展示数据用 watch，事件回调里改数据用 read。

练习 4：连线题

连线：ChangeNotifier ↔ ？　notifyListeners() ↔ ？　ObservableObject ↔ ？　objectWillChange.send() ↔ ？

✅ 答案提示：ChangeNotifier ↔ ObservableObject；notifyListeners() ↔ objectWillChange.send()。

练习 5：选型题

一个 3 人小团队要做中型电商 App，你会推荐哪种状态管理方案？理由是什么？

✅ 答案提示：推荐 Provider（或 Riverpod）。理由：团队小、要快速迭代，Provider 学习成本低、生态成熟、足以支撑中型项目；Bloc 规范强但样板代码多，小团队用会拖慢节奏。
